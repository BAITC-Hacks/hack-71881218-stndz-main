# Copilot API — §6.3

Backend читает существующий `graph.json`; роли, кластеры и скоры не пересчитывает. Базовый запуск и настройка окружения — в [README](../README.md#опциональный-backend).

## Запрос и ответ

`POST /api/ask`, `Content-Type: application/json`:

```json
{"question": "Топ 5 консолидаторов по in_kzt", "selected_gid": null}
```

`question` — строка длиной от 1 до 2 000 символов после удаления пробелов по краям. Неизвестные поля, числовой вопрос и пустая строка отклоняются с HTTP 422. Сессия переписки не хранится: каждый запрос самодостаточен.

`selected_gid` — строка из 18 цифр либо `null`; поле можно опустить. Контекст используется для вопросов о выбранном узле без явных gid, например «Покажи карточку» или «Кому он отправляет?». Явные gid в вопросе имеют приоритет: выбранный узел в этом случае не передаётся модели и не добавляется к аргументам функций. Глобальный топ не ограничивается выделенным узлом. Для общего получателя нескольких узлов перечислите их gid в вопросе: одного `selected_gid` недостаточно для запроса «с этих пятерых».

Нестроковый или неверно записанный `selected_gid` возвращает HTTP 422; корректный по формату, но отсутствующий в выгрузке — HTTP 404. При HTTP 200 ответ содержит **ровно три поля**:

| Поле ответа (HTTP 200) | Смысл |
|---|---|
| `answer` | Русский текст, сформированный из результатов функций; выводы — гипотезы |
| `gids` | Уникальные строковые gid, упомянутые в тексте ответа и найденные одновременно в результатах функций и `GraphStore`; сделать кликабельными в UI |
| `mode` | `llm`: план вызовов от модели; `rules`: ключ отсутствует или сработал фолбэк |

Неизвестный gid в тексте вопроса возвращает сообщение об отсутствии узла и пустой `gids`. Неподдерживаемый офлайн-вопрос возвращает подсказку с пустым `gids`. Это успешная обработка вопроса, а не HTTP 500. При переходе к фолбэку пояснение добавляется в `answer`; ключ и тело ошибки провайдера не возвращаются. Поля `references`, `tool_results`, `warning` и режим `fallback` не входят в согласованный контракт.

## Пять функций

Идентификатор во всех аргументах — **строка ровно из 18 цифр**. Числовой JSON-gid отклоняется, а не преобразуется после возможной потери точности. Лишние аргументы запрещены.

| Функция | Аргументы и значения по умолчанию | Семантика |
|---|---|---|
| `get_node` | `gid` | Копия карточки готовой выгрузки, включая роль, скоры и признаки |
| `neighbors` | `gid`, `direction="both"`, `limit=10` | `in` — плательщики, `out` — получатели, `both` — оба направления; связи отсортированы по сумме по убыванию |
| `common_collectors` | `gids`, `limit=10` | Пересечение прямых получателей **всех** переданных разных узлов; роль получателя может быть любой |
| `top_by` | `metric="priority_score"`, `n=10`, `role=null` | По убыванию метрики, при равенстве — gid по возрастанию; пропущенные/null-метрики не участвуют |
| `path` | `src`, `dst`, `max_hops=6` | BFS только по исходящим; кратчайший по числу рёбер путь, не по сумме или датам |

Ограничения:

- `limit` и `n`: целые 1–30; `gids`: список длиной 2–10, после удаления повторов нужны хотя бы два разных узла.
- Метрики: `priority_score`, `role_score`, `in_deg`, `out_deg`, `in_kzt`, `out_kzt`, `pass_through`. Например, `pagerank` не экспортирован в карточки JSON и недоступен этой функции.
- Фильтр `role`: шесть базовых ролей либо `boundary` для совместимости с планируемым расширением; отсутствие такой роли в данных даёт пустой список.
- `max_hops`: целое 0–8. Путь узла к самому себе содержит этот узел и ноль рёбер.
- BFS ограничен 10 000 посещённых узлов. `search_limited` сообщает о достижении лимита; `not_found_within_limit` не означает отсутствия более длинного пути.
- `has_more` сообщает об усечении таблицы результатов. `total_links`, `total_collectors`, `total_matches` — количество до ограничения выдачи.
- `sum_kzt_from_gids` — сумма наблюдаемых прямых рёбер только от указанных исходных узлов к конкретному общему получателю; не весь входящий оборот этого получателя.
- В путях нет общего «объёма прошедших денег»: агрегированные рёбра не доказывают перемещение одних и тех же средств и соблюдение временной последовательности.

## Офлайн-вопросы

Вместо `<gid>` подставьте полный идентификатор из выгрузки:

- `Карточка <gid>`
- `Входящие соседи <gid>` / `Исходящие соседи <gid>` / `Связи <gid>`
- `Кто собирает деньги с <gid> и <gid>?`
- `Топ 5 по in_kzt` / `Топ 10 консолидаторов` / `Кого смотреть первым?`
- `Путь <gid> <gid>`

Офлайн-разбор выбирает одну функцию. Произвольные составные вопросы требуют LLM или нескольких отдельных API-запросов; указанные в свободном тексте параметры, кроме размера/метрики/роли топа, не настраивают лимиты функций.

## LLM и происхождение фактов

Используется `POST {LLM_BASE_URL}/chat/completions` с `model=LLM_MODEL`, Bearer-ключом `LLM_API_KEY` и OpenAI-совместимыми `tools`. Базовый URL должен включать API-префикс (обычно `/v1`), но не `/chat/completions`. По умолчанию URL — `https://api.openai.com/v1`. Для локального сервера, требующего непустой ключ клиента, можно задать его ожидаемое тестовое значение.

Без ключа провайдер не вызывается. Если ключ есть, но модель не задана, используется фолбэк с предупреждением. Настройки считываются при старте сервера.

Цикл ограничен тремя запросами к провайдеру, шестью вызовами функций, тайм-аутом 10 секунд на HTTP-запрос. Если модель не завершила цикл в пределах лимитов, ответ строится по правилам. Ошибки сети/HTTP, неизвестные инструменты, неверные аргументы и неразбираемые ответы тоже приводят к фолбэку.

Модель может использовать gid из вопроса, допустимого контекста `selected_gid` или предыдущих результатов функций. Произвольный gid отклоняется даже тогда, когда случайно совпадает с существующим узлом. Сами функции дополнительно проверяют наличие узлов в `GraphStore`.

Финальный текст модели **не отображается**: карточки, числа и связи выводятся детерминированными шаблонами по внутренней трассе `tool_results`. Эта трасса доступна тестам сервиса, но не возвращается фронту. Так обеспечивается происхождение фактов, а не только просьба к модели «не галлюцинировать». Backend не исправляет ошибочно назначенные роли в исходной выгрузке; ограничения seed и границы обхода отражаются в карточке.

При включении внешней модели вопрос и ограниченные результаты функций передаются указанному провайдеру. Полный `graph.json` в запрос не включается. Офлайн-режим не использует внешнюю сеть.

### Передать участнику 2

Граф, карточки и топ продолжают читать статический JSON. С API связывается только панель чата. В существующий `frontend/vite.config.js` добавить dev-прокси (правку выполняет участник 2):

```js
server: { proxy: { '/api': 'http://127.0.0.1:8000' } }
```

Из панели чата отправлять:

```js
const response = await fetch('/api/ask', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ question, selected_gid: selectedId ?? null }),
})
if (!response.ok) throw new Error('Ассистент недоступен')
const { answer, gids, mode } = await response.json()
```

Отображать `answer` как текст, `mode` — как режим ответа. Каждый gid из `gids` сделать кнопкой перехода к узлу. В актуальном `App.jsx` для этого используются `setRoleFilter('all')` и `reRootTree(gid)`, как в обработчике поиска; прежнее название `focusNode` больше не актуально. На время запроса показывать загрузку; сетевую ошибку перехватывать внутри панели чата с сообщением «Ассистент недоступен». Отказ чата не должен блокировать граф и карточки. CORS для произвольных origin не включён: браузер отправляет запрос на тот же origin, а Vite перенаправляет его серверу. Для собранного сайта нужен аналогичный reverse proxy.

После нового прогона `pipeline.py` **перезапустить FastAPI и обновить страницу**. Backend загружает `out/graph.json` при старте, frontend — его копию из `frontend/public/data/` при загрузке страницы. Если используется сборка Vite, её нужно пересобрать после обновления данных.
