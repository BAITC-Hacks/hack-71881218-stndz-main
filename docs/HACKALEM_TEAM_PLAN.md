## 4. Участник 1 — Graph Intelligence (критический путь)

Файлы: `analytics/{loader,graph,features,roles,clusters,priority,evidence,temporal}.py` и `run_pipeline.py`.

### 4.1 Загрузка и граф
- Проверки из `starter.sanity_check`: сверка edges с transactions, сироты.
- `G = nx.DiGraph()` из edges, затем **`G.add_nodes_from(nodes.gid)`**. В данных 19 узлов без рёбер, среди них есть seed, и они обязательно должны попасть в выгрузку.

### 4.2 Признаки (все P0)

| Признак | Формула | Зачем |
|---|---|---|
| `in_deg`, `out_deg` | число разных плательщиков / получателей | сбор / веер |
| `in_kzt`, `out_kzt`, `in_tx`, `out_tx` | суммы и количество | сумма и число переводов — разные сигналы |
| `pass_through` | `out_kzt / in_kzt` | транзит ≈ 1 |
| `ext_inflow` | `max(0, out_kzt − in_kzt)` | **деньги пришли извне выборки**; пример: получил 0,98 млн, отдал 23 млн |
| `seed_payers` | число seed среди прямых плательщиков | прямой сбор с «курьеров» |
| `seed_reach2` | число разных seed в пределах 2 шагов вверх | **сходимость денег seed**; у 99% узлов ≤ 3 |
| `pagerank` | `nx.pagerank(G, weight="sum_kzt")` | влияние по деньгам |
| `betweenness` | `nx.betweenness_centrality(G)` (направленный) | посредник между частями сети |
| `fast_share` | доля исходящих сумм, ушедших в течение 0–2 дней после входящего | сквозной транзит |
| `sync_in_max` | максимум разных плательщиков за один день | синхронный сбор |

Почему не «достижим от seed на любой глубине»: у медианного узла деньги приходят от 7 разных seed. Признак не различает узлы.

### 4.3 Роли: правила применяются **по порядку, первое сработавшее побеждает**

Пороги откалиброваны по распределениям в данных (указаны перцентили) и в README записываются как таблица.

| # | Роль | Правило | Узлов* | Обоснование порога |
|---|---|---|---|---|
| 1 | `coordinator` | `in_deg ≥ 5` **и** `out_deg ≥ 10` | ~15 | и собирает (in_deg ≥ 5 — топ-2%), и раздаёт (out_deg ≥ 10 — топ-3%): узел управляет потоком |
| 2 | `distributor` | `out_deg ≥ 10` | ~49 | веер на ≥ 10 получателей, топ-3% |
| 3 | `consolidator` | `in_deg ≥ 5` **или** (`in_deg ≥ 3` **и** `seed_reach2 ≥ 3`) | ~50 | ≥ 5 плательщиков (топ-2%), или сбор с нескольких seed |
| 4 | `transit` | не seed, `in_deg>0`, `out_deg>0`, `0.8 ≤ pass_through ≤ 1.2` | ~67 | отдаёт дальше 80–120% полученного; у seed входящие неполные, поэтому их исключаем |
| 5 | `terminal` | `depth < 4`, `out_deg = 0`, `in_deg > 0` | ~1 070 | обход **проходил через узел** и не нашёл исходящих ≥ 5 000 KZT, значит деньги действительно остались |
| 6 | `boundary` *(расширение словаря)* | `depth = 4`, `out_deg = 0` | 444 | обход **остановился** на узле: исходящие переводы не собирались, вывод «деньги осели» делать нельзя |
| 7 | `peripheral` | всё остальное, включая 19 изолированных | ~550 | ни одно правило не сработало |

\* Пробный прогон правил на данных. Числа уточнятся после внедрения.

**Почему coordinator определяется не через «низкий pass_through».** Главные сборщики в данных отдают *больше*, чем получают (24 плательщика → 62 получателя, 19 → 61). Правило из v1 («много входящих и мало исходящих») их пропускало.

**`role_score`** — насколько узел превышает порог своей роли, всегда в диапазоне [0.5, 1]:

```text
coordinator  = 0.5 + 0.5·min(1, ((in_deg/5) · (out_deg/10))^0.5 / 3)
distributor  = 0.5 + 0.5·min(1, out_deg / 60)
consolidator = 0.5 + 0.5·min(1, max(in_deg/15, seed_reach2/5))
transit      = 1.0 − 2.5·|pass_through − 1|        (при 0.8…1.2 даёт 0.5…1.0) + 0.1 при fast_share ≥ 0.8, cap 1
terminal     = 0.9 при depth ≤ 2, 0.7 при depth = 3   (чем дальше от среза обхода, тем надёжнее вывод)
boundary     = 0.5                                     (роль определена, поведение неизвестно)
peripheral   = 0.5
```

### 4.4 Кластеры
- `nx.community.louvain_communities(G.to_undirected(), weight="sum_kzt", seed=42)`: **обязательно `seed`**, иначе результат меняется от запуска к запуску. На данных получается 87 сообществ, 8 из них содержат больше одного seed (совпадает с примечанием организаторов).
- В README оговорить, что кластеризация идёт по **неориентированной** проекции, а направление денег учитывается в ролях.
- Изолированный узел получает собственный кластер. `cluster_id` должен быть у всех 2 248 узлов.
- `sum_kzt_internal` — сумма рёбер, у которых оба конца внутри кластера.
- `hypothesis` строится по шаблону из состава ролей, формулировки осторожные:
  - ≥ 2 seed и есть consolidator → «Признаки сбора средств нескольких seed в общую точку»
  - есть coordinator и distributor → «Признаки управляемой сети распределения»
  - > 50% terminal → «Признаки конечного оседания средств»
  - > 50% boundary → «Кластер на границе выгрузки, структура неполна»
  - иначе → «Выраженной функции не выявлено»

### 4.5 Приоритет: «кого смотреть первым»

Каждый компонент — перцентильный ранг в [0, 1]. Веса простые, их легко объяснить:

```text
priority = 0.25·flow        (перцентиль max(in_deg, out_deg): концентрация потоков)
         + 0.20·structure   (перцентиль pagerank и betweenness, среднее)
         + 0.15·volume      (перцентиль log(in_kzt + out_kzt))
         + 0.15·seed_conv   (min(1, seed_reach2 / 3))
         + 0.15·external    (1 при ext_inflow ≥ 1 млн KZT, иначе ext_inflow / 1 млн)
         + 0.10·temporal    (max(fast_share, min(1, sync_in_max / 5)))

× 0.8  если is_seed        (узел уже известен; цель — найти новые узлы выше по цепочке)
cap 0.3 для boundary / peripheral / isolated
```

`top_nodes.csv` — первые 30 по `priority` (с запасом к минимуму в 20). `why` — развёрнутый evidence: роль, ключевые числа, флаги.

### 4.6 Evidence (≤ 200 символов, по-русски, с числами)

Строится шаблоном по роли, числа подставляются из признаков:
- coordinator: «Хаб: 24 плательщика → 62 получателя; получено 3,8 млн, отдано 8,6 млн KZT; средства 4 seed в 2 шагах»
- consolidator: «Сбор: 13 плательщиков (3 seed), получено 1,1 млн KZT, дальше ушло 6%»
- transit: «Транзит: получено 540 тыс., отдано 520 тыс. KZT (96%), 85% ушло в течение 2 дней»
- terminal: «Оседание: 2 плательщика, 180 тыс. KZT, исходящих ≥5 000 KZT нет (колено 2, обход продолжался)»
- boundary: «Граница выгрузки (колено 4): исходящие не собирались, вывод об оседании невозможен»

Проверка: `len(evidence) ≤ 200`, строка непустая, в ней есть цифра.

## 11. Главный принцип

Система не утверждает, что клиент преступник. Она показывает **наблюдаемые признаки, структурную роль, приоритет проверки и ограничения данных**. Окончательное решение принимает AML-аналитик.
