## D-001 — Граф строится из всех 2 248 узлов, а не из рёбер

**Статус:** ACCEPTED · PHASE 00

**Контекст.** `starter.build_graph()` создаёт `DiGraph` только из `edges`. В данных 19 seed-клиентов не участвуют ни в одном ребре, и такой граф содержит 2 229 узлов вместо 2 248.

**Альтернативы.** (а) Строить из рёбер, дописывать пропавшие узлы на этапе экспорта. (б) `G.add_nodes_from(nodes.gid)` до добавления рёбер.

**Решение.** Вариант (б).

**Обоснование.** Вариант (а) создаёт два разных представления графа, и метрики оказываются посчитаны на неполном. Замер: PageRank на графе с изолированными и без расходится до 9e-05 на узел — значения сдвигаются, а не просто дополняются нулями. Один граф на весь пайплайн исключает класс ошибок «метрика посчитана не на том объекте».

**Последствия.** `nx.hits` и часть алгоритмов чувствительнее к изолированным вершинам (см. D-004). Louvain даёт 91 сообщество вместо 69, из которых 19 — синглтоны изолированных узлов; это корректно, `cluster_id` обязан быть у всех узлов.

## D-002 — `boundary` как расширение словаря ролей

**Статус:** ACCEPTED (унаследовано из `HACKALEM_TEAM_PLAN.md` §4.3, подтверждено замерами) · PHASE 00

**Контекст.** 444 узла на 4-м колене имеют `out_deg == 0`. Наивное правило «`out_deg == 0` ⇒ конечный получатель» даёт 444 ложных стока — эта ловушка названа в ТЗ прямым текстом.

**Альтернативы.** (а) Метить их `terminal` с низким `role_score`. (б) Метить `peripheral`. (в) Ввести отдельную роль `boundary`.

**Решение.** Вариант (в).

**Обоснование.** Проверено: **все** 444 узла с `depth == 4` имеют `out_deg == 0`, исключений нет — граница обхода чистая и отделяется одним предикатом. Вариант (а) утверждает оседание там, где данных нет. Вариант (б) смешивает «обход остановился» с «признаков не выявлено» — это разные эпистемические состояния, и аналитику разница важна. ТЗ разрешает расширять словарь с документированием.

**Последствия.** Роль `terminal` осмысленна только для `depth < 4`, где обход действительно искал исходящие. `boundary` исключается из топ-приоритетов (cap 0.3) и несёт флаг `truncated_by_depth`.

## D-003 — `terminal` определяется через удержание, а не через `out_deg == 0`

**Статус:** PROPOSED — требует решения Ali · PHASE 00 · блокирует PHASE 03

**Контекст.** Ни одно из шести правил ролей в `HACKALEM_TEAM_PLAN.md` §4.3 не использует суммы — только `in_deg`, `out_deg`, `pass_through`, `depth`. Замер последствий: роль `peripheral` («признаков роли не выявлено») собирает 550 узлов и **31.3 % всех входящих денег графа** (114.7 млн KZT). Внутри — 22 узла с входящими свыше 1 млн KZT. Крайний случай: узел 3-го колена получил 4 500 000 KZT от 2 плательщиков, отдал дальше 180 300 (`pass_through = 0.04`), помечен «признаков не выявлено». 8 из топ-10 узлов по PageRank сейчас `peripheral`.

**Альтернативы.**
- (а) Оставить как есть, компенсировать приоритетом. Роль останется неинформативной, но `priority_score` поднимет такие узлы в топ.
- (б) Ввести седьмую роль `accumulator` для частичного удержания.
- (в) Переопределить `terminal`: `depth < 4` и `in_deg > 0` и `retention ≥ 0.8`, где `retention = 1 − pass_through`.
- (г) Вариант (в) плюс денежная клауза в `consolidator`: `in_kzt ≥ p95` и `in_deg ≥ 3`.

**Рекомендация.** Вариант (г).

**Обоснование.** Словарь ТЗ определяет `terminal` как «конечный получатель — деньги приходят и остаются». Узел, удержавший 96 % из 4.5 млн, соответствует этому определению буквально; привязка к `out_deg == 0` — это прокси, который ломается на узлах с одним мелким исходящим переводом. Вариант (б) вводит второе расширение словаря там, где хватает уточнения существующего. Вариант (а) оставляет жюри законный вопрос на проверке must-have №3: «почему узел с 4.5 млн — „признаков не выявлено“».

**Замеры варианта (г).** `terminal` +113 узлов (99 из `peripheral`, 14 остаются `consolidator` по порядку правил), удержано ими 53 385 960 KZT. `consolidator` +19 узлов. Итог: `peripheral` 550 → 446, её доля входящих 31.3 % → 16.3 %.

**Последствия.** Меняется таблица ролей в README и распределение в `nodes_roles.csv`. Требуется признак `retention` и порог `p95(in_kzt) = 613 779 KZT` в `config.py`. Порядок правил решает конфликт с `consolidator` без дополнительного кода.

## D-004 — HITS не используется

**Статус:** ACCEPTED · PHASE 00

**Контекст.** `starter/README.md` рекомендует `nx.hits(G)` как инструмент, разделяющий хабы и авторитеты. Проверено на реальных данных: вызов с параметрами по умолчанию бросает `PowerIterationFailedConvergence` после 100 итераций — и на графе из 2 248 узлов, и на графе из 2 229 без изолированных.

**Альтернативы.** (а) `nx.hits(G, max_iter=1000, tol=1e-6)` — отрабатывает за 0.01 s. (б) Не использовать HITS.

**Решение.** Вариант (б), с записью причины. Если хаб/авторитет понадобятся в PHASE 02 — только вариант (а) с явными параметрами.

**Обоснование.** PageRank (взвешенный по суммам) и betweenness уже покрывают «влияние» и «посредничество». HITS добавил бы два коррелирующих признака и точку отказа на демо. Рекомендация организаторов не является обязательством.

**Последствия.** Риск R3 закрыт. В README стоит упомянуть находку — это демонстрирует, что стартовый код проверяли, а не принимали на веру.

## D-005 — Точная пиновка версии networkx

**Альтернативы.** (а) `networkx>=3.1` как сейчас. (б) `networkx==3.7`. (в) Своя реализация Louvain.

## D-006 — GID передаётся строкой в JSON, int64 в CSV

**Статус:** ACCEPTED (унаследовано из team plan §3, подтверждено) · PHASE 00

**Контекст.** Максимальный GID `100000008782800100` превышает `Number.MAX_SAFE_INTEGER` (9 007 199 254 740 991).

**Решение.** В `graph.json` — строка. В CSV — `int64` по схеме ТЗ.

**Обоснование.** JSON-число потеряет младшие разряды при парсинге в браузере, и поиск по GID сломается — а это прямая проверка must-have №5 («жюри называет gid — команда находит его на схеме»). CSV читает pandas, там проблемы нет, а схема ТЗ задаёт `int64`.

**Последствия.** Экспорт конвертирует типы явно; тест проверяет round-trip максимального GID.

## D-007 — Производительность выведена из скоупа

**Статус:** ACCEPTED · PHASE 00

**Контекст.** Бюджет ТЗ — 5 минут на полный пересчёт. Замер тяжёлой части на полном графе: PageRank < 0.01 s, betweenness точный 0.88 s, `simple_cycles(≤6)` 0.03 s, Louvain 0.05 s, BFS глубины 2 по всем узлам 0.01 s. Сумма ≈ 1.0 s.

**Решение.** Betweenness считается **точный**, приближение `k=200` не используется. Оптимизация производительности исключается из скоупа PHASE 01–06.

**Обоснование.** Запас ×290. Приближённый betweenness вносит зависимость от `seed` без выигрыша. Время хакатона ограничено 5 часами, и оно оценивается через объяснимость (must-have №3), а не через скорость.

**Последствия.** Раздел README о масштабировании до 1 млн узлов остаётся текстовым, как и требует ТЗ. Если граф вырастет, точный betweenness — первый кандидат на замену.

## D-008 — Перебалансировка весов приоритета

**Статус:** PROPOSED — требует решения Ali · PHASE 00 · блокирует PHASE 05

**Контекст.** Формула team plan §4.5 задаёт `seed_conv` вес 0.15 при `min(1, seed_reach2/3)` и `temporal` через `min(1, sync_in_max/5)`. Замеры: `seed_reach2` равен нулю у 1 283 узлов (57 %), значение ≥ 3 только у 35 узлов. `sync_in_max` имеет медиану 1, p99 = 3, максимум 7; значение ≥ 5 всего у 8 узлов.

**Альтернативы.** (а) Оставить. (б) `volume` 0.15 → 0.20, `seed_conv` 0.15 → 0.10, знаменатель `sync_in_max` 5 → 3. (в) Заменить `seed_reach2` на `seed_payers` в приоритете.

**Рекомендация.** Вариант (б).

**Обоснование.** Компонент с весом 0.15, обнуляющийся у 57 % узлов, вносит меньше различающей способности, чем заявлено, а знаменатель 5 при p99 = 3 вырождает temporal-компонент в константу ≈0.2. Деньги при этом в приоритете недооценены — это та же слепота к суммам, что и в D-003. Вариант (в) даёт более узкий сигнал (`seed_payers > 0` у 490 узлов против 965), оставляем как запасной.

**Важно:** как **правило роли** `seed_reach2` работает и сохраняется — вторая клауза `consolidator` находит 14 узлов, недостижимых через `in_deg ≥ 5`.

**Последствия.** Калибровка финализируется в PHASE 05 по фактическому топ-30. Веса живут в `config.py`, README копирует формулу оттуда.

## D-009 — `fast_share` требует явной спецификации

**Статус:** ACCEPTED · PHASE 00 · реализуется в PHASE 05

**Контекст.** Формулировка team plan — «доля исходящих сумм, ушедших в течение 0–2 дней после входящего» — допускает разные реализации. Наивная («от первого входящего») даёт медиану 0.00: у многих узлов исходящие предшествуют первому наблюдаемому входящему, что является прямым следствием невидимости внешних поступлений, а не отсутствием транзита.

**Решение.** Для каждой исходящей транзакции проверяется наличие входящей в окне `[date − 2 дня, date]`; `fast_share` — доля суммы таких исходящих в общей исходящей сумме узла. Определение фиксируется докстрингом в `analytics/temporal.py`.

**Обоснование.** Число попадает в `evidence` и будет процитировано жюри («85 % ушло в течение 2 дней»). Неоднозначное определение делает его незащитимым.

**Последствия.** Признак определён только для 671 узла с исходящими транзакциями; у остальных `NaN`, в приоритете трактуется как 0.

## D-011 — Автоматика синхронизации сообщает о расхождении, но не делает `git pull`

**Статус:** ACCEPTED · 2026-09-23

**Контекст.** Требование Ali: перед началом работы всегда иметь свежую версию проекта. Реализуется хуком, а не памятью или инструкцией — автоматические действия по событию исполняет harness, а не модель.

**Альтернативы.** (а) `git pull` на `UserPromptSubmit`. (б) `git fetch` + отчёт о расхождении, решение о слиянии принимается осознанно. (в) `git pull --ff-only`.

**Решение.** Вариант (б). `.claude/hooks/git-remote-status.sh` на `SessionStart` и `UserPromptSubmit`.

**Обоснование.** Слепой `pull` на каждом промпте опасен именно в этом проекте: три участника пушат параллельно, а в рабочем дереве постоянно лежат неотслеживаемые файлы. Входящий коммит, добавляющий файл по тому же пути, останавливает merge на полпути и оставляет дерево в промежуточном состоянии. Вариант (в) безопаснее, но молча отказывает при расхождении веток и не показывает, **что именно** пришло.

Сценарий подтвердился в тот же день: `main` ушёл на 4 коммита вперёд с `pipeline.py` и React-фронтендом, при неотслеживаемых `analytics/` и `docs/` в дереве. Проверка списка входящих путей до слияния показала отсутствие коллизии — после чего `pull --ff-only` был безопасен. Слепой `pull` дал бы тот же результат случайно, а не по проверке.

**Последствия.** Хук подаёт в контекст ветку, отставание, опережение, чистоту дерева и — при отставании — входящие коммиты и файлы. Решение о слиянии остаётся явным шагом. `.claude/settings.local.json` в `.gitignore`.

## D-012 — Выгрузки PHASE 01 являются явным каркасом

**Статус:** ACCEPTED · PHASE 01 · 2026-09-23

**Контекст.** PHASE 01 должна выпускать артефакты до реализации ролей, Louvain и приоритета. Пустые или выдуманные назначения нельзя выдавать за аналитический результат.

**Решение.** До последующих фаз `nodes_roles.csv` и `graph.json` используют согласованные заглушки: пустые `role`/`evidence`, нулевые `role_score`/`priority_score` и `cluster_id = -1`; `clusters.csv` и `top_nodes.csv` содержат только заголовки. В JSON реализуется базовая схема командного плана; предложения `[ADD]` / `[CLARIFY]` из контракта не включаются до подтверждения Участником 2.

**Обоснование.** Пайплайн остаётся запускаемым после каждого checkpoint, но не маскирует ещё не реализованную аналитику под итоговую классификацию.

**Последствия.** Выгрузки PHASE 01 — технический каркас, а не готовый результат для аналитика; заполнение ролей, кластеров и приоритетов остаётся в следующих фазах. `D-005` остаётся незакрытым, поскольку `requirements.txt` принадлежит Участнику 3.

## D-013 — `seed_reach2` учитывает направленные входящие пути длиной до двух рёбер

**Статус:** ACCEPTED · PHASE 02 · 2026-09-23

**Контекст.** В графе есть циклы, поэтому простой обход с глобальным `visited` отбрасывает seed, который появляется на втором входящем шаге через цикл. Его распределение не совпадает с аудированным значением.

**Решение.** Для каждого узла собрать множество seed-GID, встречающихся на входящих направленных обходах длиной в одно или два ребра; между слоями обхода не удалять уже посещённые узлы, но дедуплицировать сами seed-GID.

**Обоснование.** На данных это воспроизводит аудированное распределение `{0: 1283, 1: 790, 2: 140, 3: 18, 4: 15, 7: 2}`. Обход простых путей давал `{0: 1293, 1: 781, 2: 142, 3: 17, 4: 13, 6: 2}`.

**Последствия.** Двухшаговый цикл может привести к тому, что seed-GID самого узла попадёт в `seed_reach2`; метрика считает seed-идентификаторы на коротких входящих walks, а не только простых путях. Это определение необходимо сохранять при использовании признака в ролях.

## D-014 — `retention` остаётся конечным при неопределённом `pass_through`

**Статус:** ACCEPTED · PHASE 02 · 2026-09-23

**Контекст.** У 42 узлов `in_kzt == 0`, поэтому `pass_through` и математический `1 − pass_through` не определены. DoD PHASE 02 допускает NaN только в `pass_through`.

**Решение.** `pass_through` сохраняет NaN; `retention` рассчитывается как `1 − pass_through`, а для этих узлов получает технический ноль. При реализации ролей retention нельзя интерпретировать без условия `in_deg > 0`.

**Обоснование.** Это сохраняет явную неопределённость исходного отношения и одновременно соблюдает контракт конечных feature-значений. Нулевой retention сам по себе не используется как доказательство удержания.

**Последствия.** `retention` присутствует в CSV как дополнительная feature-колонка; в `graph.json` не добавляется до согласования `[ADD]` Участником 2. Будущая роль `terminal` обязана требовать наблюдаемый входящий поток.
