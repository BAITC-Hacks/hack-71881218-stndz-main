# Delivery: состояние и передача требований

Зона участника 3: `backend/`, `tests/integration/`, `docs/`, `README.md`. Рабочая ветка — `feature/backend`. Источники требований: [план, §6 и §10](HACKALEM_TEAM_PLAN.md), [ТЗ, §7](../context/TASK.md). README описывает текущую реализацию `pipeline.py`, а не целевую модель плана.

## Блокеры общей приёмки

Участник команды разрешил разрабатывать Copilot параллельно исправлениям аналитики. Это исключение из порядка P0 → P2, а не снятие двух требований ниже.

Для текущей версии известны два падения интеграционных тестов:

| Проверка | Наблюдение | Владелец и необходимое исправление |
|---|---|---|
| `test_evidence_readable` | 509 evidence без чисел | Участник 1: добавить рассчитанные степени/суммы в общий шаблон периферии и шаблон изолированных узлов в `assign_roles()`; сохранить предел 200 символов |
| `test_seed_not_transit` | Один seed классифицирован как `transit` | Участник 1: исключить seed из транзитного правила; подобрать следующую роль по согласованным правилам, не по конкретному gid |

Тесты исправления не требуют. Ни ослаблять проверки, ни добавлять `xfail`, ни исправлять готовые CSV вручную нельзя. Критерий приёмки — обе проверки проходят после запуска из исходных parquet; затем полный набор `tests/integration` проходит без падений.

Воспроизведение из корня (Windows, установленная `.venv`):

```powershell
.venv/Scripts/python -m pytest tests/integration -v
```

Тесты создают независимые временные выгрузки. Для поиска проблемных узлов берите строки из свежего `nodes_roles.csv` по условиям `evidence` без цифр и `is_seed & role == "transit"`: исправление не должно зависеть от конкретного идентификатора.

## Расхождения с планом, требующие решения участника 1

- Граница обхода сейчас представлена `peripheral + truncated_by_depth`, а не отдельной ролью `boundary`. Все 444 обрезанных узла не `terminal` — это корректно учтённое ограничение текущего набора. Добавление новой роли нужно согласовать с UI.
- Правила `coordinator`, `consolidator`, `terminal` и формула приоритета отличаются от плана. README фиксирует фактические пороги и положительную прибавку за `is_seed`.
- Признаки `ext_inflow`, `seed_reach2`, `fast_share`, `sync_in_max` пока отсутствуют. Их реализацию и изменение экспорта выполняет владелец аналитики после согласования контракта.
- `sanity_check()` сверяет наличие пар `src/dst` между edges и transactions, но пока не сравнивает агрегированные суммы и количества. Требование: проверять также совпадение сумм с денежной точностью и `n_tx`.
- Для больших графов нужно заменить фиксированное ожидание 2 248 строк проверкой покрытия входного множества узлов.

## Требование участнику 2 по достоверности UI

В `frontend/src/App.jsx` показатели `delta` в карточках ролей и таблице приоритетов вычисляются из долей/скоров через остаток от деления, а не из временных наблюдений. Жюри может воспринять их как фактическую динамику.

**Требование:** убрать такие индикаторы либо заменить показателем, вычисленным из данных и имеющим явный период/базу сравнения. Числа в UI должны прослеживаться до признаков или транзакций. Также формулировки ролей и evidence следует подавать как гипотезы. Правки выполняет владелец frontend.

## Что проверено чтением реализации

- Вход: 2 248 узлов, 3 119 рёбер, 4 840 транзакций. Все узлы добавляются в граф до расчёта признаков и сообществ.
- В текущем JSON 87 кластеров; 19 изолированных узлов имеют отдельные сообщества.
- JSON использует строковые `nodes[].id`, `links[].source/target`, а не эскизный контракт из плана.
- UI загружает статический `/data/graph.json`, имеет стрелки направления, поиск и окрестность найденного узла. API не вызывается. В панели показываются восемь строк приоритетов; полный топ-30 находится в CSV/JSON.
- Backend индексирует готовый JSON и предоставляет `GET /api/health` и `POST /api/ask`.

## Реализовано: §6.3 Copilot (P2)

- `backend/graph_tools.py`: пять функций над индексами `GraphStore`, с проверкой типов, допустимых метрик, направлений и лимитов.
- `backend/copilot.py`: разбор типовых вопросов без ключа, OpenAI-совместимый клиент через существующий `httpx`, ограниченный цикл tool calling и фолбэк при ошибках.
- `backend/settings.py`: профиль `ollama` без ключа, настройки из локального `.env` и окружения, общий лимит времени вопроса. Инструкция: [OLLAMA_SETUP.md](OLLAMA_SETUP.md).
- `backend/check_copilot.py`: отдельная проверка реальной LLM по пяти функциям с замером времени. Фолбэк и неверные аргументы не засчитываются как успех.
- Локальная Ollama 0.34.3 с Qwen3 4B проверена на реальном графе: пять типов вопросов получили `mode=llm`, разовый замер на CPU — примерно 4–10 секунд после загрузки модели. План ограничен JSON-схемой с допустимыми gid из контекста.
- `POST /api/ask`: запрос `{question, selected_gid}` → функции → ответ `{answer, gids, mode}`. `mode` — только `llm` или `rules`, включая фолбэк. Трасса функций остаётся внутри сервиса для проверок; свободный текст модели исключён из фактического ответа.
- `GraphStore.load()` отклоняет числовые/дублирующиеся id, неизвестные концы связей и неагрегированные дубли рёбер.
- `tests/integration/test_api.py`: синтетический граф и имитация LLM API. Покрыты направления, циклы, отсутствующий путь/узел, общие получатели всех плательщиков, сортировка, ограничения данных, фолбэк, ошибки/некорректные аргументы провайдера, выдуманные gid, выбранный узел и точный контракт фронта.
- Инструкции запуска и контракт: [COPILOT_API.md](COPILOT_API.md). Внешний провайдер с реальным ключом отдельно не проверялся; тесты LLM работают через `httpx.MockTransport`.

Следующий шаг общей приёмки: получить исправления двух блокеров от участника 1, перегенерировать выгрузки, перезапустить API и повторить весь набор интеграционных тестов. Для подключения чата в интерфейсе участнику 2 передаётся контракт `/api/ask`.
