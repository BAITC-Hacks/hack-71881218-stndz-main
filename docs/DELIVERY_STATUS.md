## Два пайплайна: что официально и как переключаться

В `main` сейчас два пайплайна:

| | `pipeline.py` | `run_pipeline.py` + `analytics/` |
|---|---|---|
| Автор | загружен вместе с frontend (участник 2) | участник 1, по `docs/GRAPH_ENGINE_PLAN.md` |
| Выгрузки | `out/` + копия в `frontend/public/data/` | `output/` |
| Состояние | роли, кластеры, топ готовы | PHASE 01–02; роли, кластеры и топ — заглушки |

Участник 1 зафиксировал, что `pipeline.py` не является базой его движка и им не правится.

**Решение команды (2026-09-23): жюри сдаётся движок участника 1 — `run_pipeline.py` + `analytics/`.** `pipeline.py` остаётся запасным вариантом до готовности движка. Что уже переключено в зоне участника 3:

- тесты выгрузок по умолчанию запускают `run_pipeline.py` (`MONEYGRAPH_PIPELINE=legacy` — прежний);
- API ищет `output/graph.json` первым и читает формат контракта участника 1 (`gid`, `metrics`, `flags`, `edges`), приводя его к внутреннему виду; функции Copilot не менялись.

README пока описывает `pipeline.py`: он переключается на `run_pipeline.py`, когда движок выдаёт роли и интерфейс читает его `graph.json` (иначе жюри по README получит пустые роли).

### Несовместимость движка и интерфейса — требует решения участников 1 и 2

Интерфейс читает `frontend/public/data/graph.json` в формате `pipeline.py`. Движок пишет только `output/graph.json` в формате `docs/GRAPH_DATA_CONTRACT.md`. После переключения интерфейс без правок не заработает:

| Что | Интерфейс ожидает | Движок выдаёт |
|---|---|---|
| Файл | `frontend/public/data/graph.json` | только `output/graph.json` |
| Узел | `id`, метрики на верхнем уровне, `truncated_by_depth` | `gid`, метрики в `metrics`, `flags[]` |
| Связи | `links[{source, target}]` | `edges[{src, dst}]` |
| Топ | `top[]` | нет, есть `rank` в узле |
| История | `timeseries[]`, `transactions[]` | нет |

Варианты: (а) движок дополнительно пишет копию в формате интерфейса во `frontend/public/data/`; (б) интерфейс переходит на контракт движка и сам собирает `top`; поля `timeseries`/`transactions` в любом случае добавляет движок. Решение и контракт — на Checkpoint участников 1 и 2; API участника 3 уже читает оба формата.

Переключение без правки кода:

```powershell
# тесты выгрузок на движке участника 1
$env:MONEYGRAPH_PIPELINE = "engine"; .venv/Scripts/python -m pytest tests/integration/test_outputs.py -v
# API на выгрузке движка
$env:MONEYGRAPH_GRAPH_JSON = "output/graph.json"; .venv/Scripts/python -m uvicorn backend.main:app --port 8000
```

На текущем движке 8 из 14 проверок выгрузок проходят; 6 падают из-за незаполненных ролей, кластеров и топа (ожидаемо до PHASE 03–06).

**Python 3.12+.** `networkx` зафиксирован на 3.7 по D-005 участника 1; эта версия требует Python 3.12+. README обновлён. Если команда решит поддерживать Python 3.10–3.11, нужна другая версия (например, 3.4.2) и повторный замер кластеров участником 1.

| Проверка | Наблюдение | Владелец и необходимое исправление |

## Расхождения с планом, требующие решения участника 1

- Граница обхода сейчас представлена `peripheral + truncated_by_depth`, а не отдельной ролью `boundary`. Все 444 обрезанных узла не `terminal` — это корректно учтённое ограничение текущего набора. Добавление новой роли нужно согласовать с UI.
- Правила `coordinator`, `consolidator`, `terminal` и формула приоритета отличаются от плана. README фиксирует фактические пороги и положительную прибавку за `is_seed`.
- Признаки `ext_inflow`, `seed_reach2`, `fast_share`, `sync_in_max` пока отсутствуют. Их реализацию и изменение экспорта выполняет владелец аналитики после согласования контракта.
- `sanity_check()` сверяет наличие пар `src/dst` между edges и transactions, но пока не сравнивает агрегированные суммы и количества. Требование: проверять также совпадение сумм с денежной точностью и `n_tx`.
- Для больших графов нужно заменить фиксированное ожидание 2 248 строк проверкой покрытия входного множества узлов.

## Требование участнику 2 по достоверности UI

В `frontend/src/App.jsx` показатели `delta` в карточках ролей и таблице приоритетов вычисляются из долей/скоров через остаток от деления, а не из временных наблюдений. Жюри может воспринять их как фактическую динамику.

**Требование:** убрать такие индикаторы либо заменить показателем, вычисленным из данных и имеющим явный период/базу сравнения. Числа в UI должны прослеживаться до признаков или транзакций. Также формулировки ролей и evidence следует подавать как гипотезы. Правки выполняет владелец frontend.

## Реализовано: §6.3 Copilot (P2)

- Локальная Ollama 0.34.3 и Qwen3 4B: пять функций проверены с настоящим `mode=llm`; режим не требует внешнего API-ключа. План ограничен JSON-схемой с допустимыми gid из контекста.
- `backend/settings.py` загружает профиль из `.env`/окружения; `backend/check_copilot.py` проверяет реальные вызовы и не засчитывает фолбэк. Инструкция: [OLLAMA_SETUP.md](OLLAMA_SETUP.md).
- Проверены сборка frontend, чтение `output/graph.json` и живой запрос по цепочке Vite → FastAPI → Ollama (`200 / llm`).

- `backend/graph_tools.py`: пять функций над индексами `GraphStore`, с проверкой типов, допустимых метрик, направлений и лимитов.
- `backend/copilot.py`: разбор типовых вопросов без ключа, OpenAI-совместимый клиент через существующий `httpx`, ограниченный цикл tool calling и фолбэк при ошибках.
- `POST /api/ask`: запрос `{question, selected_gid}` → функции → ответ `{answer, gids, mode}`. `mode` — только `llm` или `rules`, включая фолбэк. Трасса функций остаётся внутри сервиса для проверок; свободный текст модели исключён из фактического ответа.
- `GraphStore.load()` отклоняет числовые/дублирующиеся id, неизвестные концы связей и неагрегированные дубли рёбер.
- `tests/integration/test_api.py`: синтетический граф и имитация LLM API. Покрыты направления, циклы, отсутствующий путь/узел, общие получатели всех плательщиков, сортировка, ограничения данных, фолбэк, ошибки/некорректные аргументы провайдера, выдуманные gid, выбранный узел и точный контракт фронта.
- Инструкции запуска и контракт: [COPILOT_API.md](COPILOT_API.md). Внешний провайдер с реальным ключом отдельно не проверялся; тесты LLM работают через `httpx.MockTransport`.

Обновление аналитики, формата JSON и подключение UI согласуются с владельцами соответствующих зон.
