# Graph Data Contract

Что аналитический движок отдаёт наружу: UI (Участник 2), backend/Copilot (Участник 3), жюри.

**Статус:** предложен Участником 1 по итогам PHASE 00. Базируется на `HACKALEM_TEAM_PLAN.md` §3; расхождения и дополнения помечены **[ADD]** и **[CLARIFY]** — требуют подтверждения на Checkpoint 1.

**Правило изменений:** поля можно **добавлять**. Переименовывать, менять тип или удалять существующие — только с уведомлением обоих участников.

## 2. `nodes_roles.csv`

Ровно **2 248 строк**. Обязательные колонки по ТЗ — первые шесть, порядок сохраняется.

| Колонка | Тип | Диапазон / словарь | Гарантия |
|---|---|---|---|
| `gid` | int64 | `100000000011452100` … `100000008782800100` | уникален, совпадает с `nodes.parquet` |
| `role` | str | `coordinator`, `distributor`, `consolidator`, `transit`, `terminal`, `boundary`, `peripheral` | непустой, всегда из словаря |
| `role_score` | float | [0.5, 1.0] | не NaN |
| `cluster_id` | int | ≥ 0 | заполнен у всех узлов, включая изолированные |
| `priority_score` | float | [0.0, 1.0] | не NaN |
| `evidence` | str | ≤ 200 символов | непустой, содержит хотя бы одну цифру, русский язык |

**[ADD]** Дополнительные колонки — ТЗ разрешает («лишние колонки добавлять можно»). Нужны жюри для проверки must-have №3 и UI для карточки узла:

`depth`, `is_seed`, `in_deg`, `out_deg`, `in_kzt`, `out_kzt`, `in_tx`, `out_tx`, `pass_through`, `retention`, `ext_inflow`, `seed_payers`, `seed_reach2`, `pagerank`, `betweenness`, `component_id`, `component_size`, `fast_share`, `sync_in_max`, `truncated_by_depth`.

`pass_through` может быть NaN у 42 узлов с `in_kzt == 0`; `fast_share` — у узлов без наблюдаемых исходящих транзакций (1 554 узла в текущих данных). В `graph.json` оба значения сериализуются как `null`; при расчёте приоритета неопределённый `fast_share` трактуется как 0. `sync_in_max` — максимум разных плательщиков за календарный день и равен 0 при отсутствии входящих транзакций.

**`role` — словарь.** Шесть ролей обязательны по ТЗ. `boundary` — задокументированное расширение словаря: узлы, на которых обход остановился (`depth == 4`, `out_deg == 0`). Их **нельзя** трактовать как конечных получателей.

## 3. `clusters.csv`

Строка на кластер. Сумма `n_nodes` по всем строкам = **2 248**.

| Колонка | Тип | Гарантия |
|---|---|---|
| `cluster_id` | int | уникален; совпадает со значениями в `nodes_roles.csv` |
| `n_nodes` | int | ≥ 1 |
| `n_seed` | int | 0 … 81 |
| `sum_kzt_internal` | float | сумма рёбер, у которых **оба** конца внутри кластера |
| `top_gids` | str | GID через `;`, до 5 штук, по убыванию `priority_score` |

**[CLARIFY]** `top_gids` — разделитель `;` без пробелов, чтобы не конфликтовать с CSV-запятой. В `graph.json` то же поле приходит массивом строк.

Каждый из 19 изолированных узлов образует собственный кластер размера 1.

### Словарь флагов

| Флаг | Условие | Смысл для UI |
|---|---|---|
| `truncated_by_depth` | `depth == 4` и `out_deg == 0` | «Граница выгрузки: исходящие не собирались» — блокирует вывод об оседании |
| `seed_inflow_incomplete` | `is_seed == true` | входящие извне выборки не наблюдаются, `pass_through` недостоверен |
| `outflow_exceeds_inflow` | `out_kzt > in_kzt` | 377 узлов; для не-seed это признак внешнего притока |
| `isolated` | `in_deg == 0` и `out_deg == 0` | 19 узлов, все seed |
| `external_funding` | `ext_inflow ≥ 1 000 000` | 80 узлов |

## 6. Жёсткие правила сериализации

1. **`gid`, `src`, `dst` в JSON — всегда строки.** Максимальный GID `100000008782800100` превышает `Number.MAX_SAFE_INTEGER` (2^53 − 1 = 9007199254740991). Число в JSON потеряет младшие разряды, и поиск по GID в UI сломается — а это прямая проверка must-have №5. В CSV `gid` остаётся `int64` по схеме ТЗ.
2. **NaN → `null`.** Python `json` по умолчанию пишет `NaN`, что невалидно по JSON и роняет `JSON.parse` в браузере. Сериализация идёт с `allow_nan=False` и явной заменой на `None`.
3. **Даты — строки `YYYY-MM-DD`**, без временной зоны.
4. **Кодировка UTF-8 без BOM**, `ensure_ascii=False` — иначе русский `evidence` раздувает файл и нечитаем при отладке.
5. **Порядок узлов и рёбер стабилен** (сортировка по `gid` / `src,dst`) — иначе diff между прогонами бесполезен.

## 7. Гарантии для потребителей

Что Участник 2 и Участник 3 могут считать данностью:

- ровно 2 248 узлов, ни один не потерян, включая 19 изолированных;
- `cluster_id` и `role` заполнены у каждого узла — ветка «роль неизвестна» в UI не нужна;
- `evidence` непустой у каждого узла — плейсхолдер не нужен;
- `rank` есть только у 30 узлов, у остальных `null` — фильтр «топ» строится по `rank != null`;
- `priority_score` сопоставим между узлами (перцентильные компоненты), `role_score` — **нет**: он измеряет соответствие узла своему правилу и между разными ролями не сравним. В UI не строить единый рейтинг по `role_score`.

## 8. Как проверить контракт

Тесты в `tests/analytics/test_contract.py` (PHASE 06) валидируют: количество строк, типы, диапазоны, словарь ролей, длину `evidence`, сумму `n_nodes`, монотонность `priority_score` по `rank`, round-trip максимального GID через JSON, отсутствие `NaN` в JSON, побайтную идентичность двух прогонов.
