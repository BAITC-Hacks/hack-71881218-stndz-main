# «Граф денег»: как работает проект

Аналитик начинает с 81 стартового клиента и получает сеть из 2 248 узлов. Инструмент помогает выбрать, кого проверить первым, объясняет наблюдаемые связи и показывает, каких данных не хватает. Результаты — гипотезы по структуре переводов, а не выводы о виновности.

## Кто за что отвечает

| Часть | Задача | Результат |
|---|---|---|
| Аналитика | Проверить parquet, посчитать признаки, роли, кластеры и приоритет | `run_pipeline.py` и `analytics/` → три CSV и `graph.json` |
| Интерфейс | Найти клиента и исследовать сеть | направленный граф, карточка, топ-30, кластеры, операции, выгрузки |
| API и ассистент | Дать интерфейсу согласованные данные и ответы | FastAPI, рекомендации по пробелам данных, устойчивость и Copilot |

Роли, кластеры и приоритеты рассчитывает один движок. Интерфейс и ассистент используют эти результаты и не назначают клиенту собственную версию роли.

## Путь от данных до экрана

```text
data/*.parquet
    → python run_pipeline.py
    → output/: три CSV + graph.json
        → FastAPI → React-интерфейс
        → sync-data → локальная копия frontend
```

`graph.json` содержит узлы, направленные связи, кластеры и реальные транзакции. Все GID передаются строками: 18-значный идентификатор нельзя превращать в JavaScript number без потери точности.

Интерфейс сначала получает `/api/graph`. Если API недоступен, открывается синхронизированная локальная выгрузка с явным индикатором и возможностью переподключиться. Граф, поиск, топ, кластеры, операции и CSV продолжают работать. Серверные рекомендации, устойчивость и ассистент требуют работающего API.

`sync-data` переносит все четыре официальных файла из `output/`, а не только JSON. Если хотя бы один отсутствует, запуск сообщает ошибку и просит пересчитать данные. Так таблица на экране и скачанный CSV относятся к одному результату.

## Рабочий сценарий аналитика

1. Открыть все 30 строк приоритетов и выбрать клиента либо найти полный GID.
2. Посмотреть направление переводов, его плательщиков и получателей. Цвет означает роль, размер помогает сравнивать приоритет. Интерфейс указывает, какая часть сети сейчас показана.
3. Прочитать evidence, суммы и ограничения в карточке. Серверная карточка объясняет пробелы данных и предлагает следующий запрос аналитика.
4. Перейти к кластеру: размер, число стартовых клиентов, внутренний оборот и гипотеза.
5. Проверить реальные входящие и исходящие операции выбранного клиента.
6. Скачать `nodes_roles.csv`, `clusters.csv` и `top_nodes.csv`.
7. При необходимости смоделировать удаление топ-N узлов или задать вопрос ассистенту.

Поиск включает изолированных клиентов. Если переводов нет, это показывается как отсутствие наблюдаемых операций, а не как ошибка. Если запрос не удался, интерфейс показывает ошибку и повторную попытку.

## Как читать выводы

У узлов четвёртого колена исходящие не собирались: `boundary` означает границу выгрузки. Нельзя делать вывод, что деньги остались на таком счёте. `terminal` — гипотеза удержания в пределах наблюдаемого периода, банка и порога переводов.

`role_score` показывает соответствие правилу роли, а `priority_score` — порядок проверки внутри текущей выборки. Это разные показатели; ни один не является вероятностью виновности. Приоритеты основаны на степенях, структуре, суммах, сходимости стартовых узлов и временных признаках. Формулы и пороги собраны в [README](../README.md).

Расчёт устойчивости удаляет выбранное число узлов по приоритету и сравнивает связность графа. Он не моделирует будущие действия клиентов и не принимает решение о блокировке.

## Ассистент и API

Аналитик выбирает узел и спрашивает «Кому он отправляет?». Запрос содержит текст и выбранный строковый GID:

```json
{"question": "Кому он отправляет?", "selected_gid": "<gid>"}
```

Ответ содержит `answer`, `gids` и `mode`. По ссылке GID открывается соответствующий клиент. Явные идентификаторы в вопросе важнее текущего выделения.

Без модели типовые вопросы разбираются по правилам. Опциональная LLM выбирает функции: карточка, соседи, общие получатели, топ по показателю и направленный путь. Числа и фактический ответ строятся из результатов этих функций. При ошибке провайдера включается режим правил. Настройка локальной модели: [OLLAMA_SETUP.md](OLLAMA_SETUP.md); контракт чата: [COPILOT_API.md](COPILOT_API.md).

| Возможность | Endpoint |
|---|---|
| Состояние и источник | `GET /api/health` |
| Граф | `GET /api/graph` |
| Карточка с рекомендациями | `GET /api/nodes/{gid}/card` |
| Операции клиента | `GET /api/nodes/{gid}/transactions` |
| Результаты движка | `GET /api/exports/{filename}` |
| Устойчивость | `GET /api/resilience?n=10` |
| Вопрос по графу | `POST /api/ask` |

## Запуск и обновление

Установка зависимостей описана в [README](../README.md). Из корня репозитория, с активированной виртуальной средой:

```sh
python start_dev.py
```

Launcher пересчитывает данные, запускает API на `http://127.0.0.1:8000` и интерфейс на `http://127.0.0.1:5173`. Swagger находится по адресу `http://127.0.0.1:8000/docs`. Другие порты: `python start_dev.py --api-port 8001 --web-port 5175`. `Ctrl+C` останавливает оба сервера.

После самостоятельного запуска `python run_pipeline.py` перезапустите API, выполните `npm --prefix frontend run sync-data` и обновите страницу. Для preview нужна новая сборка. Старой альтернативной реализации `pipeline.py` в проекте больше нет.

## Что проверять перед показом

```sh
python -m pytest tests -q
npm --prefix frontend run lint
npm --prefix frontend run build
```

Проверки выгрузок запускают официальный движок во временной папке. Они контролируют покрытие всех узлов, схемы, заполненность и объяснения, граничные случаи, детерминизм и время. API проверяется отдельно; финальная проверка интерфейса проходит по [DEMO_SCRIPT.md](DEMO_SCRIPT.md).

На показе нужно найти произвольный GID, объяснить роль по числам, показать направления переводов и различие `terminal`/`boundary`, открыть все 30 приоритетов, кластер и реальные операции, скачать согласованные CSV. Текущее состояние передачи фиксируется в [DELIVERY_STATUS.md](DELIVERY_STATUS.md).
