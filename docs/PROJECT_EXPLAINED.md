# «Граф денег»: как работает проект простыми словами

Этот файл объясняет, за что отвечают три участника, что должно быть на экране и как части проекта соединяются в готовое решение для аналитика.

## 1. Кто что делает

| Участник | Простыми словами | Результат |
|---|---|---|
| 1 — аналитика | Считает, кто с кем связан, какие у узлов признаки и кого стоит проверить первым | `pipeline.py` → три CSV и `graph.json` |
| 2 — интерфейс | Показывает результаты так, чтобы аналитик мог разобраться в сети | Граф, поиск, карточки, топ и панель чата |
| 3 — backend / delivery | Делает ответы на вопросы по графу, проверяет результат и объясняет запуск проекта | FastAPI, Copilot, тесты, README и инструкции |

Ключевая договорённость: роли, кластеры и приоритеты рассчитывает аналитика. Интерфейс и Copilot используют готовые результаты, а не назначают каждому клиенту собственную версию роли.

## 2. Что уже сделано в нашей части

- **Copilot:** `POST /api/ask` отвечает на вопросы по готовому графу.
- **Пять функций:** карточка узла, соседи, общие получатели нескольких узлов, топ по показателю и направленный путь.
- **Контекст выбранного клиента:** можно выделить узел и спросить «Кому он отправляет?», не переписывая его длинный идентификатор.
- **Режим без внешнего ключа:** по умолчанию типовые вопросы разбираются по правилам; для настоящей локальной LLM можно включить [Ollama](OLLAMA_SETUP.md).
- **Подключение LLM:** адрес, модель и ключ задаются переменными окружения. Модель выбирает функции, а фактический ответ строится из их результатов.
- **Тесты:** автоматический «жюри-проверяльщик» проверяет выгрузки и работу API.
- **README:** запуск, реальные правила ролей, формулы, ограничения данных и план масштабирования.
- **Инструкция фронтендеру:** [COPILOT_API.md](COPILOT_API.md).

Реальный внешний LLM-провайдер ещё требует проверки с ключом. Автоматические тесты проверяют его протокол имитацией API, не выполняя платных запросов.

## 3. Что должно быть на фронте

Ниже — целевой пользовательский сценарий после завершения работы всех участников. Граф и карточки уже существуют; подключение чата выполняет участник 2.

### Поиск клиента

Аналитик вводит полный `gid`. Интерфейс находит клиента, показывает его на графе и открывает карточку. `gid` везде остаётся строкой: его нельзя превращать в JavaScript number, иначе длинный идентификатор может потерять последние цифры.

### Граф переводов

- Кружочки — клиенты.
- Стрелки — кто кому переводил деньги.
- Цвет — предполагаемая роль.
- Размер помогает заметить более приоритетные узлы.
- Выбор узла открывает его карточку; раскрытие связей помогает исследовать окружение.

Необязательно рисовать всю сеть одновременно. Важно, чтобы выбранный клиент, его связи и направление переводов были понятны. В актуальном интерфейсе есть дерево связей с раскрываемыми ветками.

### Карточка клиента

Карточка должна отвечать на вопросы:

1. Какая роль назначена?
2. Почему — какие числа это подтверждают?
3. Сколько клиент получил и отправил?
4. Сколько у него разных плательщиков и получателей?
5. Какой приоритет проверки?
6. Какие ограничения данных влияют на вывод?

Например, у узла на границе выгрузки должно быть понятно: **«Мы не видим дальнейшие переводы», а не «Деньги точно остались здесь»**. Скор роли и приоритет — показатели правил, а не вероятность виновности.

### Топ и кластеры

Топ помогает понять, **с кого начать проверку**. Кластеры показывают группы тесно связанных узлов и гипотезы о наблюдаемой структуре. Из списка приоритетов можно перейти к карточке клиента. Полный топ-30 и сведения о кластерах доступны в выгрузках; интерфейс должен давать понятный доступ к этим результатам.

Любые числовые показатели на экране должны иметь источник в данных. Декоративные `Δ`, рассчитанные из долей или скоров, нельзя выдавать за реальную динамику переводов; это требование передано владельцу интерфейса.

### Чат Copilot

Аналитик выбирает узел и спрашивает:

> Кому он отправляет деньги?

Чат передаёт вопрос и идентификатор выбранного узла серверу. Сервер находит исходящие связи и возвращает ответ с кликабельными `gid`. По нажатию на идентификатор интерфейс переходит к соответствующему клиенту.

В панели нужны:

- поле вопроса и кнопка отправки;
- индикатор загрузки;
- текст ответа;
- кликабельные идентификаторы клиентов;
- обозначение режима: `llm` или `rules`;
- сообщение «Ассистент недоступен», если сервер не отвечает.

Ошибка чата не должна блокировать граф, карточки или поиск. Они продолжают работать на статической выгрузке.

## 4. Как соединяются части проекта

```text
Исходные переводы: data/*.parquet
                  │
                  ▼
        Аналитика участника 1
                  │
                  ▼
    Роли, приоритеты, кластеры
       CSV + готовый graph.json
            │             │
            ▼             ▼
      React-интерфейс   Наш FastAPI
            │             ▲
            └── вопрос ───┤
            ◄── ответ ────┘
```

**Участник 1 считает.** Из сырых данных получаются результаты с объяснениями.

**Участник 2 показывает.** Интерфейс читает копию `graph.json` из `frontend/public/data/` и позволяет исследовать сеть.

**Наш сервер отвечает на вопросы.** Он загружает `out/graph.json` в память. LLM выбирает нужные функции поиска, функции извлекают реальные данные, шаблон превращает их в текст. Самостоятельно придумывать роли, суммы или связи модель не может.

**Наши тесты проверяют сдачу.** Они выявляют потерянные узлы, ошибки в выгрузках, нарушения ограничений данных и дефекты API.

## 5. Договорённость с фронтендером

С API связан только чат. Граф, карточки и топ продолжают читать статический JSON.

Запрос:

```json
{"question": "Топ 5 по priority_score", "selected_gid": null}
```

Если клиент выбран, вместо `null` передаётся его строковый gid. Явные идентификаторы в вопросе имеют приоритет перед выделением в интерфейсе.

Ответ содержит ровно три поля:

- `answer` — текст;
- `gids` — список существующих узлов, упомянутых в ответе;
- `mode` — `llm` или `rules`, включая режим после ошибки провайдера.

Участник 2 добавляет прокси `/api` на FastAPI и панель чата. В актуальной версии интерфейса для перехода из ответа используется `reRootTree(gid)` со сбросом фильтра роли, как при поиске. В старом описании этот переход назывался `focusNode(gid)`.

Полный контракт, пример `fetch`, обработка ошибок и лимиты — в [COPILOT_API.md](COPILOT_API.md#передать-участнику-2).

## 6. Как будет выглядеть хорошее демо

1. Запускаем пайплайн и показываем три готовых CSV.
2. Открываем интерфейс, выбираем клиента из топа или ищем произвольный gid жюри.
3. Показываем его связи и объясняем роль по числам из карточки.
4. Сравниваем узел на границе выгрузки и узел с признаками оседания, объясняем разницу.
5. Спрашиваем Copilot о выбранном клиенте и переходим по ссылке из ответа к его контрагенту.
6. Показываем результаты тестов и объясняем ограничения анализа.

Главный результат: аналитик понимает **кого проверить, почему и какие данные ещё нужно запросить**. Система формирует гипотезы, а не обвинения.

## 7. Что осталось участникам

### Участнику 1

- Исправить evidence без чисел: последняя проверка ветки backend выявила 509 таких строк.
- Исключить seed из транзитного правила: один seed сейчас ошибочно получает `transit` при неполных входящих данных.
- Согласовать окончательные пороги и изменения контракта данных, чтобы README, интерфейс и API соответствовали аналитике.

### Участнику 2

- Подключить чат по готовому API-контракту.
- Сделать переходы по gid и локальную обработку ошибок чата.
- Проверить отображение ограничений данных и достоверность числовых индикаторов.

### Нам, участнику 3

- Настроить `LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL` и проверить выбранного провайдера с реальным ключом.
- После исправлений аналитики повторить интеграционные тесты и актуализировать документацию, если изменятся правила.
- Вместе с командой пройти сквозной сценарий демо.

Без настройки модели Copilot работает по правилам. С локальной Ollama доступен настоящий режим `llm` без внешнего API-ключа. Известные блокеры общей приёмки описаны в [DELIVERY_STATUS.md](DELIVERY_STATUS.md).

## 8. Запуск и обновление данных

Полная установка описана в [README](../README.md). После установки зависимостей из корня репозитория:

```powershell
.venv/Scripts/python pipeline.py --no-viz
```

Backend в первом терминале:

```powershell
.venv/Scripts/python -m uvicorn backend.main:app --port 8000
```

Frontend во втором терминале:

```powershell
npm --prefix frontend run dev
```

Обычно интерфейс доступен на `http://localhost:5173`, Swagger — на `http://localhost:8000/docs`, проверка сервера — на `http://localhost:8000/api/health`.

После нового пересчёта пайплайна нужно **перезапустить API и обновить страницу**: оба компонента загружают данные при старте, а не следят за файлом автоматически. При использовании собранного frontend нужно также обновить сборку.

Финальная проверка:

```powershell
.venv/Scripts/python -m pytest tests/integration -v
```

Решение готово к общей приёмке, когда тесты проходят, интерфейс находит произвольный gid, роли объясняются по реальным числам, а чат возвращает проверяемые ответы и корректно обрабатывает недоступность модели.
